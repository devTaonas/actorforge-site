Dataset SQL Query - DuckDB Joins, GROUP BY & Window Functions

Run one SQL query (DuckDB) over your Apify datasets, CSV/JSON/Parquet URLs or pasted rows: filter, join, GROUP BY, pivot, window functions, nested JSON. Result rows go to a new dataset (+ CSV/Parquet). $0.20 per 1,000 result rows + $0.001 per 1,000 rows read.

Run on Apify →See pricing

What it does

Ask any question of your scraped data in SQL, without leaving Apify. Pick one or more Apify datasets, add CSV, TSV, JSON, JSON Lines or Parquet file URLs or paste rows, and run one SQL query on a real analytical engine (DuckDB): WHERE filters, JOINs across datasets (e.g. jobs × companies, products × competitor prices), GROUP BY with counts, sums and averages, window functions (rank, running totals, QUALIFY row_number() = 1 to keep the latest row per key), PIVOT, regexp_extract, date maths and nested JSON access (address.city, tags[1], json_extract). Each source becomes a named table; every column and its detected type is listed in the log. The result rows land in a new dataset you can export, chain to another Actor or send to Make/n8n/Zapier, and can also be saved as CSV, Parquet or JSON Lines files. Use it after a scheduled scrape to build daily reports, clean and reshape rows for a CRM, or deduplicate with exactly the rule you want. It is read-only by design: one SELECT-type statement, no file or network access from SQL, and with limited permissions it can read only the datasets you pick. $0.20 per 1,000 result rows + $0.001 per 1,000 input rows read, so a GROUP BY over 100,000 rows that returns 20 rows costs about $0.10.

Limits and honest notes

  • Dialect: DuckDB SQL (PostgreSQL-like): CTEs, all join types, GROUP BY ALL, window functions, QUALIFY, PIVOT/UNPIVOT, list and struct functions, regexp_*, strftime/date_trunc, json_extract and ->> operators. Each source is a table (rows, dataset_1 …, file_1 … or your names; the first is also called data); the log lists every column with its type.
  • One query per run. It must be a single read-only statement (SELECT, WITH, FROM-first, VALUES, TABLE, PIVOT/UNPIVOT, SUMMARIZE, DESCRIBE). Table names are fixed by the input; the query cannot open other files, URLs or databases.
  • Datasets: with limited permissions the run can read only the datasets picked in the Datasets field (or passed by ID via the API or an integration). If a source cannot be read, the query is not run (a partial join would be wrong) and nothing is charged.
  • Integrations: when run after another Actor, set Datasets to ["{{resource.defaultDatasetId}}"] to query the triggering run's results (limited permissions grant read access only to datasets given in the Datasets field).
  • Input rows are capped by Max input rows (default 2 million, up to 10 million) and by your spend limit; if a table is cut short, the log and OUTPUT say so and aggregates cover only the loaded rows.
  • Column types are detected from the data: all dataset rows for JSON sources, the first 100,000 rows for CSV. CSV IDs with leading zeros may be read as numbers unless the column also has non-numeric values; cast in SQL if needed.
  • Files are downloaded once, up to 200 MB each. Private and internal network addresses are refused at every redirect hop.
  • The query runs with the run's memory (DuckDB gets about 55% and spills to disk) and stops after the query timeout (default 300 s).
  • Result values: BIGINT/HUGEINT beyond 2^53 are returned as text, DATE as YYYY-MM-DD, TIMESTAMP as ISO 8601, BLOB as text.
  • When the query returns no rows, the run adds one free row with _status and _message and still succeeds. Invalid input or SQL errors add a free status row and fail the run with the DuckDB error message.
